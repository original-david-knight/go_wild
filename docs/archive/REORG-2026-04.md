# Repository Reorganization — Design Doc

Status: **Approved with post-Codex revisions** (interview + audit + Codex review 2026-04-17; all open questions resolved; implementation plan pending)
Owner: David Knight
Audience: internal team consumers of this codebase

## Problem

The repo has grown organically into 19 top-level directories mixing libraries, apps, and vestigial scaffolding. The current structure gets in the way of using this as a *library of packages* across multiple projects:

- **Apps and libraries are peers at the top level.** A consumer skimming the repo can't tell `gowild_agent_net` (app) from `gowild_agentic_loop` (library). Codex review (2026-04-17) confirmed the correct split: **2 pure apps** (`gowild_agent`, `gowild_agent_manager` — `package main` at root), **2 mixed modules** (`gowild_agent_net`, `gowild_objectives` — library root + `cmd/` binaries), **12 pure libraries** (the rest), plus **1 hidden app** at `cmd/mcp-broker-server/` built from the root `go.mod`. (`mottopedia` was also a mixed module; being deleted entirely — see cleanup PR.)
- **Module paths stutter.** `knight.fm/gowild/gowild_data` repeats the umbrella name. The `knight.fm` vanity path is aspirational, not backed by a real `go-import` redirector.
- **Local dev relies on `replace` directives.** Every cross-module refactor requires touching N `go.mod` files. The existing `go.work` file is supposed to handle this but coexists with `replace` directives and is underused.
- **Vestigial top-level scaffolding.** Root-level `cmd/`, `pkg/`, `api/`, `internal/`, and a root `go.mod` are leftovers from an earlier layout. Unclear what `agentnode/` and `mcp-broker-server/` are.
- **Go version drift.** Modules span `go 1.23`, `go 1.24.0`, and `go 1.24.2`.
- **No public-API discipline.** Every exported symbol in every package is reachable by every consumer. Refactoring any internal helper is a potential breaking change.

## Non-goals

- **No public open-source publishing.** Consumers are internal only; this doc does not commit to semver, vanity import paths, or external API stability guarantees.
- **No behavioral changes.** This reorganization is structural only. Tests, builds, and runtime behavior must be unchanged after the migration.
- **No new abstractions.** We are not splitting packages, merging packages, or introducing new layers beyond what is described here.

### 3. Import paths

All paths rooted at the real GitHub repo:

```
github.com/original-david-knight/go_wild/<module>
```

Examples:

```
github.com/original-david-knight/go_wild/my
github.com/original-david-knight/go_wild/data
github.com/original-david-knight/go_wild/agentic_loop
github.com/original-david-knight/go_wild/codexllm
github.com/original-david-knight/go_wild/agent_net
github.com/original-david-knight/go_wild/apps/agent
github.com/original-david-knight/go_wild/apps/agent_net_server
github.com/original-david-knight/go_wild/apps/mcp-broker-server
```

**Drop the `gowild_` prefix** on every directory and import path. The umbrella path (`go_wild`) already provides the namespace; `gowild_data` under it stutters.

Note: `go_wild` uses an underscore rather than the conventional hyphen because that is the actual GitHub repo name. Legal in Go module paths; non-blocking.

### 4. Versioning

**No tags.** Consumers use `go get <path>@main` (or `@<sha>`), which Go resolves at that moment to a pseudo-version (`v0.0.0-<timestamp>-<sha>`) and records in the consumer's `go.mod`. Important: `go.mod` stores pseudo-versions, not the literal string `@main`.

Rationale: internal consumers; per-module tag streams are not worth the coordination overhead. If a production app needs stability, it pins to a specific SHA — no tagging required.

**Known caveat — multi-module lockstep (called out in Codex review).** A single commit that changes multiple libraries produces multiple pseudo-versions, all with the same SHA. Consumers that depend on more than one of those libraries must update them in **one `go get` invocation** (`go get A@main B@main` together) to pick them up atomically. Separate invocations may drift if new commits land in between. For single-consumer internal use this is usually fine; for multi-consumer environments, plan around it.

### 5. Local development workflow

- **`go.work` at repo root** stitches all modules together for local dev. Contributors edit across modules without `go get` cycles.
- Long-term target: **zero `replace` directives** in any `go.mod`. Apps in CI/prod read their real `go.mod`, which records pseudo-versions against the remote repo.
- **Short-term during migration**: `replace` directives stay until the new module paths exist on GitHub. Removing them is a *separate* PR from the path rewrite (see revised migration approach).

### 5a. Private-repo setup for external consumers (new — added in Codex revision)

The GitHub repo is private (confirmed 2026-04-17). Consumers in other projects must set:

```bash
go env -w GOPRIVATE=github.com/original-david-knight/*
```

Without this, `go get` routes through the public proxy and sumdb and will fail to resolve private modules. Add a short note to the top-level `README.md` documenting this, alongside the `go get` examples.

Each consumer project also needs Git credentials that can read the repo (SSH key, GitHub CLI token, or `~/.netrc` entry) for `go get` to succeed.

### 6. Go version

Every module's `go.mod` pins `go 1.25` (floor). Drift across 1.23 / 1.24.0 / 1.24.2 is eliminated. The workspace is already running `1.25.5` (matches current root `go.mod` / `go.work`), so this costs nothing.

### 7. Public vs. internal API

Each library uses `internal/` subpackages to hide implementation details. Only the package root and intentionally-exported subpackages are importable by consumers outside the module.

Rationale: an intentional public API surface is easier to refactor later without breaking callers. Cost: more thought required when adding a new package — "is this public or internal?"

### 8. Cleanup

Deleted as part of this reorganization (confirmed by audit):

- Root-level `go.mod` and `go.sum` (after `cmd/mcp-broker-server/` moves to `apps/`).
- Root-level `cmd/` (empty after the move).
- Root-level `api/`, `configs/`, `internal/`, `test/` (all `.gitkeep`-only).
- Root-level `/agentnode` and `/mcp-broker-server` (stray ELF binaries; also add to `.gitignore`).

### 9. App-specific files move under their app

- `Dockerfile.agent-net` → `apps/agent_net_server/Dockerfile`
- `render.yaml` (deploys `agent_net`) → `apps/agent_net_server/render.yaml`

## Migration approach (outline only — full plan is a separate doc)

**Revised after Codex review** — the original "rename PR = rewrite paths + remove `replace`" combination is not atomic-safe. Codex flagged that removing `replace` before the new module paths exist remotely means `GOWORK=off` builds in the PR are fake. The fix: split path rewrite from `replace` removal. Also add an explicit publish-and-verify step.

1. **Cleanup PR** — delete stray root binaries (`/agentnode`, `/mcp-broker-server`), delete empty scaffolding (`api/`, `configs/`, `internal/`, `test/`), delete the `mottopedia/` module entirely and remove its references from `go.work`, `README.md`, `AGENTS.md`, `docs/module-deps.md`. Add the stray binaries to `.gitignore`.
2. **App extraction PR** — move `gowild_agent` and `gowild_agent_manager` (both `package main`) and the three mixed modules' `cmd/` binaries under `apps/`. Move `cmd/mcp-broker-server/` to `apps/mcp-broker-server/` and give it its own `go.mod`. Delete root `go.mod`/`go.sum` and the now-empty `cmd/`. Move app-specific Docker/deploy files alongside (`Dockerfile.agent-net`, `render.yaml`). **Keep `replace` directives in this PR** so builds work locally and in CI.
3. **Rename PR** — drop `gowild_` prefix from directory names, update module paths in every `go.mod`, update every import statement in every `.go` file. Update `go.work`. Bump every module's `go` directive to `1.25`. **`replace` directives stay in place** (updated to point at the renamed paths). Builds go green with `GOWORK=on` (local, CI) and remain fake under `GOWORK=off` until PR #4 lands.
4. **Publish + replace-removal PR** — after PR #3 is merged to `main`, the new module paths resolve on GitHub via pseudo-versions. Now: remove all `replace` directives. Each `go.mod` records real pseudo-versions pinned to `@main`. Run `go mod tidy` in every module. Verify `GOWORK=off go build ./...` passes in each module independently. This PR is the one that proves the dependency model works.
5. **`internal/` PR(s)** — for each library, audit which *currently-public subpackages* have cross-module importers. Move only the unimported or internal-use ones under `internal/`. Do not move anything used by sibling modules. Land library-by-library.

### Why the split matters

- PR #2 (app extraction) and PR #3 (rename) are independently reviewable and independently revertible.
- PR #4 (replace-removal) is the one that exercises the production dependency-resolution path. Keeping it separate means the dependency-model failure mode (if any) shows up in a small, focused PR instead of being entangled with a big mechanical rewrite.
- PR #5 (`internal/`) is safe only after a cross-module import audit. Hiding a package that `gowild_agent_node` or `gowild_deep_research` currently imports will break those consumers.

### Cross-module import facts that PR #5 must respect

Codex and direct source-import inspection confirmed that today's public cross-module surface includes:

- `gowild_tools/broker`, `gowild_tools/amazon`, `gowild_tools/shopify`, `gowild_tools/supplier`, `gowild_tools/supplier/providers/cjdropshipping` — imported by other modules' code.
- `gowild_agentic_loop/mcp` — imported by other modules.
- `gowild_agent_net/server` — imported by `gowild_agent_net`'s own tests; remains public inside the library.
- Source-level direct imports the `go.mod` audit missed: `gowild_objectives` imports `gowild_agent_node`; `gowild_deep_research` imports `gowild_claudellm`, `gowild_codexllm`, `gowild_tools`, `gowild_agentic_loop`.

None of these block the rename. All of them constrain PR #5.

### Group cohesion — `llm` group fails, `agent` group partially fails

The interview approved two grouped modules (`llm` and `agent`) on the guess that packages inside each group co-evolve. The actual dep graph contradicts this:

**`llm` group (proposed: `agentic_loop` + `codexllm` + `claudellm`)**

- `codexllm/go.mod`: **no dependency** on `agentic_loop` or `claudellm`.
- `claudellm/go.mod`: **no dependency** on `agentic_loop` or `codexllm`.
- `agentic_loop/go.mod`: only depends on `my`.

Conclusion: these are **three independent LLM SDK wrappers**. `codexllm` and `claudellm` are not adapters to `agentic_loop`'s Provider interface. The grouping was a naming guess that the code does not justify.

**`agent` group (proposed: `agent` + `agent_node` + `agent_data`)**

- `gowild_agent` depends on `agent_data` (direct), plus `agentic_loop`, `claudellm` (indirect), `crypto`, `data`, `knowledge_graph`, `my`, `tools`.
- `gowild_agent_node` depends on `agentic_loop`, `deep_research`, `my`, `tools` (direct), plus `agent_data`, `codexllm`, `crypto`, `data`, `knowledge_graph` (indirect). Does **not** depend on `gowild_agent`.
- `gowild_agent_data` depends on `data`, `knowledge_graph` (direct), plus `agentic_loop`, `my` (indirect). Does **not** depend on `gowild_agent` or `agent_node`.

Conclusion: `agent_data` is a foundational library that `agent` builds on. `agent_node` is a peer to `agent` (both use `agent_data`, neither imports the other). Tighter than `llm`, but not the "three-peas-in-a-pod" that "agent group" implies.

**Resolved (2026-04-17): Option A — ungroup both.** Final layout has **14 library modules**, one per existing package: `my`, `data`, `objectives`, `tools`, `knowledge_graph`, `deep_research`, `polymarket`, `crypto`, `agentic_loop`, `codexllm`, `claudellm`, `agent_data`, `agent`, `agent_node`. Reflected in Decision 2 above.

Consumers that import `agent` as a library inherit all of it. If consumers in practice only use specific sub-capabilities, some of what's currently public in `agent` may be a candidate for `internal/` or for extraction into smaller packages.
